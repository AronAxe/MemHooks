# Mem0 adapter mapping — memhooks/v2

Use this reference when the active memory backend is **Mem0** (Platform or compatible OSS SDK).

Mem0-native retrieval controls belong under:

```yaml
backends:
  mem0:
    ... Mem0-specific controls ...
```

The MemHooks core preserves and structurally merges this mapping but does not interpret its internal keys.

## Retrieval boundary

MemHooks is retrieval-routing infrastructure. Loading a hook should use Mem0 search/get operations as needed; it must not call memory-add/update/delete operations merely because a hook exists.

## Recommended namespace conventions

For current Mem0 v3-style search, a Mem0 adapter may interpret:

```yaml
backends:
  mem0:
    filters:
      user_id: alice
    top_k: 10
    threshold: 0.1
    rerank: false
    enable_graph: true
```

Recommended meanings:

| Key | Meaning |
|---|---|
| `filters` | Mem0 search filters, including required entity scope and optional metadata/category/date conditions |
| `top_k` | maximum search results requested |
| `threshold` | minimum relevance threshold when supported |
| `rerank` | request Mem0 reranking when supported |
| `enable_graph` | use Graph Memory retrieval when supported by the active Mem0 deployment |

These are Mem0 adapter conventions, not universal MemHooks fields.

## Current Mem0 search model

Current Mem0 v3 documentation places entity IDs **inside `filters`** for search/get operations.

Relevant scope identifiers include:

- `user_id`
- `agent_id`
- `app_id`
- `run_id`

Example:

```yaml
backends:
  mem0:
    filters:
      AND:
        - user_id: alice
        - run_id: session-123
```

The adapter should construct the exact filter shape expected by the actual Mem0 Platform/OSS version in use.

Mem0 filters can also target metadata, categories, timestamps, and logical/comparison conditions where supported.

## MemHooks entities are not Mem0 entity IDs

This distinction is important.

A MemHooks core entity:

```yaml
entities:
  - name: Authentication
    type: CONCEPT
    salience: 0.9
```

is a **retrieval cue**.

A Mem0 `user_id`, `agent_id`, `app_id`, or `run_id` is a **memory-scope identifier**.

Do not automatically convert a MemHooks entity named `Authentication` into a Mem0 `user_id` or `agent_id`. Scope identifiers belong explicitly in `backends.mem0.filters` or in trusted runtime configuration.

## Example

```yaml
schema: memhooks/v2

recall_queries:
  - query: "What did we previously decide about authentication retries?"
    priority: 0.9
    entities:
      - Authentication
    tags: [reliability]
    backends:
      mem0:
        top_k: 8
        threshold: 0.15
        rerank: true

backends:
  mem0:
    filters:
      user_id: project-agent
```

The query, priority, entity, and tag are MemHooks core intent. Search tuning and memory scope are Mem0-native.

## Mapping generic MemHooks cues

### `recall_queries`

Use each applicable query as the natural-language Mem0 search query.

Do not collapse several precise recall questions into one vague query merely to reduce API calls if doing so would damage retrieval specificity.

### `priority`

Use MemHooks priority to decide which recall requests receive context budget first. Do not substitute Mem0's returned search score for MemHooks priority or vice versa.

### `entities`

Use entity names to sharpen query text where useful. Current Mem0 retrieval already includes entity matching as part of its retrieval pipeline, but MemHooks entity cues remain conceptually separate from Mem0 memory-scope IDs.

### `resources`

Mem0 does not need to expose a universal resource class for the MemHooks core to work. If a named MemHooks resource corresponds to something the host runtime can fetch, retrieve it through the runtime. Provider-specific resource identifiers can stay under `backends.mem0` when needed.

### `tags`

When the Mem0 deployment stores equivalent metadata/categories, an adapter may translate generic tags into appropriate filters. Do not invent metadata that was never stored.

### `exclude`

Where the requested exclusion maps cleanly to Mem0 filters, use native negative filtering. Otherwise post-filter retrieved memories before they enter context.

## Filters

Mem0 Platform v3 supports structured filter logic around entity identifiers and other fields. Use the exact syntax supported by the connected version.

Examples may include:

```yaml
backends:
  mem0:
    filters:
      OR:
        - user_id: alice
        - agent_id:
            in: [travel-agent, support-agent]
```

or metadata/category/date constraints when appropriate.

The MemHooks core does not validate this internal filter object. Provider-specific validation belongs in the Mem0 adapter.

## Search tuning

Current Platform v3 documentation exposes search controls including `top_k`, `threshold`, and `rerank`.

These should remain provider-native:

```yaml
backends:
  mem0:
    top_k: 12
    threshold: 0.2
    rerank: true
```

The adapter should not assume defaults are permanent; omit values when runtime/provider defaults are desired.

## Graph Memory

Mem0 Graph Memory layers graph relationships alongside vector retrieval and can return related entity context in addition to ordinary search hits.

When the active deployment supports it, a query may carry:

```yaml
backends:
  mem0:
    enable_graph: true
```

This is a retrieval hint only. It must not cause graph writes or graph configuration changes simply because MemHooks loaded.

## Provider namespace merging

MemHooks structurally merges `backends.mem0` root → leaf:

- nested mappings recursively merge;
- local scalars replace parent scalars;
- local lists replace parent lists;
- query-local Mem0 configuration overlays scope-level Mem0 configuration.

Example parent:

```yaml
backends:
  mem0:
    filters:
      user_id: alice
    threshold: 0.1
```

query-local overlay:

```yaml
backends:
  mem0:
    top_k: 5
    rerank: true
```

Effective query configuration retains the user filter and threshold while adding `top_k` and `rerank`.

## Platform versus OSS

Mem0 Platform and OSS capabilities/configuration can differ. The adapter must inspect/use the API actually connected rather than pretending every documented Platform feature exists in OSS or vice versa.

When a hint is unsupported, ignore or translate it safely; never claim the control was applied when it was not.
